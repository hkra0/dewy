# aqua 鱼缸节点优化方案

日期：2026-10-24。范围：设计方案，尚未修改运行代码或设备配置。

## 1. 目标与边界

沿用 ESP32 → MQTT → 树莓派 → Worker → 浏览器四层架构，改善鱼缸节点的本地提醒、温度异常处理与状态可理解性。仓库中的节点 id 是 `aqua`，不新增 `auqa` 别名。

- ESP32 是本地报警、触摸交互、喂食提醒运行状态的唯一执行端；断开 MQTT 后仍应工作。
- 树莓派继续存储并转发节点设置、提供数据与展示，不再运行一份相同的喂食算法。
- 青鳉的温度参数属于节点配置；通用代码不按 `node_id == 'aqua'` 或鱼种名称分支。
- 本轮仍是人工喂食记录与提醒，不包含自动投饵器。
- 保留四个主视图、现有卡片、暖琥珀呼吸灯与短时温度指示，不新增鱼缸专属导航页。

讨论里的 10℃、31.5℃、30 分钟变化 1.8℃及积分速率，均作为可调的试运行参数，不称为经过验证的生理模型或通用饲养标准。尤其不由水温单独推断缺氧、疾病或真实饥饿程度。

## 2. 当前实现与需要先修的基础问题

| 位置 | 现状 | 对本次优化的影响 |
| --- | --- | --- |
| `feeding.cpp` | 每日指定小时重置 `is_fed`；10 秒内可撤销；NVS 保存记录 | 不能表达多日间隔、跳过、温度暂停；按小时重置可能在该小时内重启后重复执行 |
| `led.cpp` | 高低温持续闪烁；未喂食持续暖琥珀呼吸 | 冬季低温会长期报警；没有确认、自动停止闪烁及夜间提醒窗口 |
| `sensors.cpp` | 非阻塞请求 DS18B20 转换后立即读取；首次有效缓存初值为 0 | 需明确转换完成时序；从未成功读到水温时也可能短暂把 0 当有效缓存 |
| `network.cpp` | mDNS/MQTT 重连循环可阻塞几十秒到数分钟，失败重启 | 断网期间主循环不能可靠更新触摸、LED 与本地算法 |
| `mqtt_handler.py` | 数据通过 `dict.update()` 累加 | 固件省略无效水温或旧 `fed_time` 时，后端仍可能展示旧值 |
| `sensor_aggregator.py` | 所有普通数值都算修剪均值 | 数字 `fed=0/1` 已有被平均为小数的风险；新增状态码也不能按连续量处理 |
| `settings.js` | 动态表单只支持 number/text | 模式、开关要通过通用 boolean/select 能力扩展 |
| 灯控链路 | 一套全局 `auto_light`、`light_status` 与手动覆盖 | 第二盏独立灯不能直接套入而不处理多执行器状态 |

这些是本次功能的必要基础工作，不扩大为全项目重构。

## 3. 温度监测与报警

### 3.1 有效样本先于业务判断

明确区分新鲜有效样本、短暂缓存、无效/过期样本。传感器层保存 `has_valid_sample`、最后成功采样时间和失败计数，不以某个数值初值表示“曾经成功”。

DS18B20 用“发起转换 → 等转换完成 → 读取 → 安排下一轮”的非阻塞流程，等待时间依据所选分辨率。保留现有其他传感器滤波，不为此增加采样频率。

短暂缓存可供界面展示，但不得重复进入温差历史或重复累加提醒积分。持续失败后上报明确的 `water_temp_valid=false`、样本年龄和 `water_temp=null`，后端清除旧快照；旧固件没有这些字段时保留兼容处理。

85℃是 DS18B20 温度寄存器的上电复位值，不能笼统称为硬件“断线错误码”；-127℃按所用 DallasTemperature 库的断线标记处理。驱动先判读取质量，报警模块接收统一有效性状态。

### 3.2 四类独立条件

| 条件 | 推荐策略 | aqua 试运行值 |
| --- | --- | --- |
| 高温 | 超线确认触发，回差退出 | 31.5℃，回差 0.5℃ |
| 低温 | 可单独启用；保留其它鱼缸使用能力 | aqua 关闭持续低温闪烁 |
| 温度变化 | 有时间戳的固定容量环形缓冲，比较窗口两端短时中位数 | 30 分钟，绝对变化 ≥1.8℃ |
| 探头异常 | 连续失败/样本过期后触发，连续成功后恢复 | 先用约 15 秒确认，实机调整 |

温差检测只在历史覆盖足够且连续有效时启用，重启或数据断档后重新预热。不用“当前值减上一帧”，也不用窗口最大值减最小值冒充 30 分钟净变化。事件保留升温/降温方向；若以后需要检测短时尖峰，应另立规则。

高温、低温与温差均需去抖与恢复确认。具体确认次数与窗口允许断档写入实现常量并测试，先避免把所有工程细节暴露成设置项。

### 3.3 报警事实与灯光确认分离

每类报警维护 `active`、事件标识、触发时间、确认/静默截止时间。灯只显示当前最高优先级，全部有效报警仍可上报。

- 优先级：探头故障 → 高温 → 已启用的低温 → 温差变化。
- 短按确认当前显示的报警，此次触摸不再记喂食；持续按住到释放也不能再触发跳过。
- 讨论中的默认行为保留：持续闪烁最多 15 分钟，之后静默 6 小时；短按也可提前静默。
- 静默期间关闭该报警闪烁，但网页保留原因和“已确认”；实际恢复才清除 `active`。
- 新的另一类报警不继承旧报警的静默；同一条件需稳定恢复后再次触发才算新事件，不能靠阈值抖动反复闪烁。
- 静默到期且条件仍成立可重新提示；重启恢复静默期限，避免重启后重复闪烁。无可信时钟时保守抑制重复提示，并显示时间待同步。

## 4. 喂食提醒：保留两种模式

提供 `daily`（兼容现有每日提醒）和 `temperature_accumulation`（温度积分提醒）。已有部署继续用 `daily`；aqua 在启用新版配置时显式选第二种。UI 称“提醒进度”，不称“消化率”或“饥饿度”。

### 4.1 积分与每天一次的判定

在新鲜、有效且允许提醒的水温下，按实际经过时间累加：

```text
score = min(score_cap, score + rate(T) × valid_elapsed_hours)
```

每分钟整合一次已覆盖的有效温度区间即可，无需等到整小时才处理，也不能用当前温度回填几个小时的未知历史。单次允许积分的样本间隔有上限；超出则暂停并重新建立连续采样。低温、高温、探头故障时暂停积分和提醒，恢复后仍受当天处理标记约束。

讨论速率作为可调整的首版曲线：

| 水温区间 | 每小时积分 |
| --- | --- |
| T < 10℃ 或 T ≥31.5℃ | 0，暂停提醒 |
| 10 ≤ T <12.5℃ | 1.50 |
| 12.5 ≤ T <15℃ | 2.25 |
| 15 ≤ T <20℃ | 4.60 |
| 20 ≤ T <31.5℃ | 5.00 |

阈值先用 100、上限 120；四档速率由节点 schema 的普通数值参数表达，不引入复杂曲线编辑器。切点和允许区间统一校验，区间边界一处实现，避免 31.5℃同时允许提醒与暂停。

为符合讨论中的“早上决定今天是否提醒”，**每天仅在提醒窗口内首次取得有效条件时评估一次**：积分够才开始提醒，否则当天等待下一日。建议窗口 07:00–21:00；开机错过 07:00 可在窗口内补评估，窗口结束不补闪灯。保存当天评估日期，重启不能再评一次。

这是对原伪代码的必要修正：若每小时在 07:00–21:00 都检查，13.5℃下次日下午积分满 100 就会提醒，无法保证讨论中的“第三天早上”。每日评估使用完整本地日期，时间戳存 UTC，间隔和灯效使用单调时间。

### 4.2 喂食、跳过和提醒相互独立

运行状态分别保存：真实喂食记录、积分、当天动作、下次允许提醒日期。页面状态由这些事实派生为“等待 / 待喂食 / 已喂食 / 今日已跳过 / 温度暂停 / 探头异常 / 时间待同步”。

| 动作 | 积分 | 真实喂食记录 | 后续提醒 |
| --- | --- | --- | --- |
| 确认已喂食 | 清零 | 写入真实时间 | 当日不再提醒，后续按模式计算 |
| 默认跳过/21:00 自动跳过 | 保留 | 不改 | 设置下次允许提醒为次日窗口 |
| 可选“跳过整轮” | 清零 | 不改 | 从零开始下一轮 |
| 10 秒内撤销 | 恢复操作前快照及应计进度 | 恢复原记录 | 恢复原提醒资格 |

默认跳过不倒扣预计积分，直接保存 `next_prompt_date`。讨论公式按“未来 20 小时”倒扣，不能适配 07:00 和 21:00 两个跳过时刻，也不能保证未来水温不变；日期门控能准确表达“今天不提醒，明天再提醒”。

### 4.3 触摸行为

按键统一在释放时判定短按/长按（例如 1.5 秒），不能先在按下时确认喂食、随后再当成长按跳过。

1. 正在闪烁报警：本次手势只确认报警。
2. 处于撤销窗口：短按撤销最近的喂食/手动跳过，完整恢复快照。
3. 正在提醒：短按已喂食，长按跳过。
4. 无提醒且水温允许：沿用短按记录主动喂食；已处理当天的普通短按查看温度。
5. 低温暂停时：短按冰蓝轻闪三次作为提示，不自动记已喂食；高温/无效温度同样给出对应原因。

不引入双击或更多手势。静默后的报警仍有效，但不应永久吞掉之后每一次喂食触摸。

### 4.4 恢复与 Flash 写入

NVS 分离配置与运行状态，保存版本号、积分、完整日期、最后喂食时间、当天动作、下次提醒日期和必要静默期限。已有 `feed_st` 记录做一次迁移；旧的 `tm_yday` 不包含年份，不能直接当完整日期恢复。

动作发生时保存，积分限频检查点保存（建议 30–60 分钟），只在值变化时写配置；不在 10ms 主循环或每次重连时重复写相同内容。断电的积分误差控制在检查点区间内。掉电区间没有可靠水温，不自动补积分；NTP 未同步可采样与报警，暂停依赖日历的自动提醒，不伪造 `00:00` 喂食时间。跨年、时钟校正和长时间停机都需有确定行为。

## 5. 通信、配置与数据兼容

- 将 WiFi/mDNS/MQTT 重连改为有退避和短超时的分步流程，正常运行中不因 Broker 掉线持续重启；连接尝试必须有时间预算，本地循环能持续运行。
- 保留 `/config/set` 与 `/config/state`，设置仍在 `node_settings.<node_id>`；纯业务配置不进入 Worker。
- `config_apply` 先解析成候选配置，验证类型、范围、时刻关系及温度区间，再整体应用；失败保留旧值。回报实际生效值、配置协议版本与错误，不把“已发布”当成“设备已应用”。
- 通用后端只按 schema 检查类型/边界，不解析青鳉业务；固件承担跨字段约束。新增 boolean/select 的通用渲染和序列化，旧 number/text 原样兼容。
- 旧 `feed_reset_hour` 在新字段缺失时迁移为提醒开始小时；低温阈值保留，新增独立启用开关。历史配置的默认填充不得悄悄把现有鱼缸切换到青鳉策略。
- 同步真实配置与 `hardware_config.example.toml`，使用现有 `label` i18n 约定，修正示例中的 `label_key` 差异。构建脚本改为显式选择目标节点并解析 TOML，避免写死 aqua/sub1 或用正则读配置。
- MQTT 数据增加版本标记，保留旧 `fed`/`fed_time`，但 `fed=1` 只能表示真实已喂食；跳过和暂停不能伪装为已喂食。清空时间发送 null，避免后端残留。
- 增加 `feeding_state`、`feeding_score`、`next_prompt_date`、温度有效性和报警状态。状态元数据不当作额外指标卡自动铺满页面；首次上报、动作和报警变化即时发送，正常传感器仍按原周期。
- 声明 `metrics` 的节点要同步允许所需字段。服务端按数据版本维护字段更新/清空规则与最后接收时间；节点超时显示过期，不能继续呈现为实时正常。
- 聚合器通过通用指标元数据区分 continuous/latest，状态值取最新；积分可按快照取最新。状态字符串、日期留在快照元数据，不新增 SQLite 固定列。
- 当前先不新增喂食事件表/事件 API。十分钟状态归档不能替代精确事件日志；若以后要看完整喂食历史，再单列事件协议、去重、断网补传和 DAL 设计。
- 扩容时计算 JSON 容量、序列化缓冲区与 MQTT 包头/主题开销，检查溢出和 publish 返回值，不能继续假设 256/300 字节文档与 512 字节包一定够用。

## 6. 界面与灯效

水温卡继续用 `--metric-water-temp`，在卡片副文案显示样本过期/报警与静默状态；喂食卡保留原位置，显示明确动作和原因，不把所有“未喂食”都标红。

- 待喂食：暖琥珀呼吸；等待/今日已处理/夜间：熄灭。
- 高温红色、故障黄色、温差变化使用独立可辨认的短闪节奏；低温提示仅在交互时冰蓝三闪。
- 沿用当前 `get_dynamic_amber_breath()`、完整亮度范围、抖动和平滑过渡，避免本次顺便换成绿光或另一套呼吸曲线。
- 网页使用文字说明状态，颜色仅辅助；现有 CSS 变量、圆角变量、中英文文案和键盘可访问约定继续适用。
- 模式与常用参数放现有节点动态设置卡。首版不增加网页远程“已喂食/跳过/消警”按钮，避免额外控制协议和鉴权改造。
- 无 viewer key 静默规则保持；旧固件无新状态字段时，继续渲染原喂食卡。

若新增 JS 模块，仍需注册 Worker 静态模块与 modulepreload；新增状态展示不能靠前端读取水温重算一套报警/积分逻辑。

## 7. 鱼缸灯：独立后续阶段

第一阶段只落实监控和提醒，继电器为可选硬件。先确认灯具供电方式、短断电记忆时间、长断电是否复位、开关序列和实际模式，不预设 400ms 或每次三次通断一定正确。优先使用已有隔离外壳的控制器，若灯具允许再考虑适配的低压侧控制；方案不包含裸露市电接线操作。

实现时对上层仍暴露 `state=True/False`，模式序列封装在执行器设备端，配置参数描述启动模式与通断时序，不把“白+紫”写进 `core.logic.light`。

关键约束：

- 连续收到 ON 必须幂等：只有已知 OFF→ON 执行启动序列；现有调度会重复发 ON，不能每轮都切一次颜色。
- OFF 可随时取消序列，执行非阻塞，重连/保留消息重放不能导致反复闪灯。
- 没有光色反馈时只报告“目标模式/序列已完成”，不宣称已验证真实光色；断电恢复状态不明时应先按已验证的复位时序建立确定状态。
- 将灯状态、手动覆盖、回报抑制和乐观状态按 `(node_id, actuator_id)` 隔离，定时配置也需支持独立灯；保留现有全局配置与接口兼容迁移。
- 由服务端 `node_capabilities()` 统一下发灯能力，不凭 aqua 名称显示按钮。
- 若要求断网仍按时开关，日程由灯设备本地执行，Pi 下发配置与手动命令；不能让两个独立调度同时争用灯。

完成上述灯控多设备设计后再接入鱼缸灯，避免改一盏灯影响植物补光与拍照补光。

## 8. 实施顺序与验收

| 阶段 | 主要文件 | 可验收结果 |
| --- | --- | --- |
| P0 基础可靠性 | 固件 sensors/network；MQTT 快照、聚合器 | 无首次假 0℃；断网不阻塞触摸；失效水温不残留；状态不被平均 |
| P1 报警与交互 | 独立 temperature_alarm 模块；led/feeding/main | 高温/温差/故障可区分；静默及恢复正确；一次手势只有一个动作 |
| P2 温度积分提醒 | feeding/config；NVS 迁移；节点 schema | daily 兼容；积分模式、次日跳过、自动跳过、撤销与掉电恢复可验证 |
| P3 展示与配置闭环 | settings/dashboard/metrics/i18n；通用配置验证 | 卡片状态清楚；boolean/select 可保存；实际生效/等待回报可区分 |
| P4 可选灯控 | 执行器固件/驱动；灯控多设备链路 | 重复 ON 不切色；OFF 可抢占；两盏灯互不干扰 |

P1/P2 的判断逻辑使用无 Arduino/FastLED/网络依赖的 C++ 状态机，注入时间、温度样本及动作；通过 PlatformIO native 测试验证，避免只测一份 Python 仿制算法。后端继续 stdlib unittest 和现有模块打桩。

必须覆盖：

1. 13.5℃连续有效采样：第一次喂食后第二天 07:00 不提醒，第三天提醒；18.6℃下次日提醒。评估频率、边界与当天只处理一次均符合定义。
2. 07:00 手动跳过与 21:00 自动跳过都只推迟到次日窗口；温度随后改变不破坏日期门控，暂停条件仍优先。
3. 低温、高温、断线、首次未转换完成、缓存过期及恢复；无效时不积分，不产生虚假温差。
4. 30 分钟稳定/渐变/突变/缺样；历史未满不触发；恢复回差不反复新建报警。
5. 报警短按不记喂食；长按不先触发短按；撤销恢复原积分和记录；15 分钟自动静默与 6 小时到期行为正确。
6. 跨午夜、跨年、窗口内重启、NTP 延迟/前后校时、掉电恢复及 millis 回绕。
7. 保留配置重放不重复写 NVS；非法配置不部分生效；最大载荷不截断；旧固件和新旧配置组合有确定回退。
8. Broker/WiFi 长期断开时本地仍能采样、报警和操作，恢复后上报当前状态；网页能标识过期数据。
9. 字符串元数据不生成杂乱指标卡，状态归档取最新，中英文本、暗色主题与旧节点显示正常。

构建检查：`python -m unittest discover -s tests -t .`、`pio run -e esp32s3mini`；加入 native 环境后运行对应固件测试。前端改动需人工核对页面；若新增模块或改变静态资源打包，再运行 `npx wrangler deploy --dry-run`。继电器序列最后用测试负载验证后再接实际灯具。
